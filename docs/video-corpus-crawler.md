# 按用户画像筛选 30 个字幕视频

## What was added

`scripts/crawl_eval_videos.py` 读取一个用户画像，自动搜索并筛选 30 个不同的 B 站视频。
每个入库视频都必须有可用的第 1P 字幕，并经模型判断为主题相关、有实质教学内容。
达到 30 条时至少 28 条为适合当前画像的候选，最多 2 条为困难负样本候选；负样本不足时
使用适合画像的候选补齐。候选不足时保留实际数量，不用低质量视频凑满。
部分库中的困难负样本同样不得超过 10%，没有正样本时不保留负样本。

“正样本候选/困难负样本候选”均是自动筛选结果，人工标签仍为待复核。
负样本配额和下述阈值是本项目的采集规则，不是行业评估标准。

复用项目的 `build_models()`、`EnhancedSearch.search()` 与
`BilibiliSource.metadata()/subtitles()`，并复用 `score_candidates(..., stage="screen")`。
搜索继续通过千问 EnhancedSearch MCP，
元数据和字幕继续通过项目安装的 `bilibili-api-python`，不新增依赖。

### 筛选流程

1. 从画像推导学习任务、必要知识、实践形式，生成短搜索词。提示词不包含预设技术名列表。
   下一批生成会参考每个搜索词的候选数量、筛选结果和淘汰原因。
2. 使用搜索标题、简介和摘要，按完整画像中的主题、学习目标、水平、偏好与时长初筛。
   不再清空画像约束，减少不适合用户的候选；未通过的候选不请求 B 站元数据和字幕。
   通过标题初筛后，实际章节仍可能被字幕审核判为困难负样本或淘汰。
3. 获取元数据及第 1P 字幕，根据实际章节审核。具体知识讲解、步骤或案例可作为实质内容；
   宣传、空泛路线和纯课程目录不能因整套课程标题带“实战”而入库。
   “介绍”“基础”“环境准备”不作为关键词黑名单，是否适合取决于实际内容与画像。
4. 主题相关、内容充实且 `quality_score >= 0.65` 才可进入候选池。
   `suitable=true`、`fit_score >= 0.65` 且 `mismatch=none` 作为正样本候选；
   `suitable=false`、`fit_score < 0.65` 且有明确水平、形式、任务或时长差异
   作为困难负样本候选。低质量、无关、没有解释的“不适合”均淘汰。
5. 寻找更大的池：默认目标为 45 个合格候选，再按匹配分、内容充实分选择最终 30 条，
   困难负样本最多 2 条，且占最终库不超过 10%；每保留 1 条负样本需要至少 9 条正样本。
   可以替换先发现的较弱候选，不再找到前 30 个字幕视频就结束。

字幕按连续内容组成带时间戳的审核片段，每片最多 1600 字符。超过 15 片时均匀选取
开头、中间及结尾的 15 片，审核输入最多约 24000 字符；记录完整/抽样覆盖情况。
模型必须引用本视频实际提供的片段 ID，跨视频或不存在的证据会被拒绝。
抽样审核和模型判断不能保证整段视频的技术正确性，仍需人工复核。

查询生成最多 10 批，每批最多 3 个新词；最多检查 120 个不同 BV 号，
视频请求之间间隔 1 秒。达到 45 个合格候选且能组成 30 条时提前结束。
预算耗尽时仍会选出已发现的合格候选；如果已组成 30 条，采集也算完成。
HTTP 412、字幕登录错误、搜索或初筛服务失败等情况会停止并保留已采结果。
未达到目标时退出码为 1，达到目标时退出码为 0；不会用重复或无字幕视频凑满数量。
已存在的输出快照会被拒绝覆盖，重新运行需指定新目录。

## Why it exists

为单画像推荐评估准备固定候选库。初筛保留完整画像，负样本按数量和比例双重限制，
避免正样本不足时负样本占据大部分库。字幕可用于后续 RAG 和 Diversity@5，
冻结标题、简介和统计数据可让不同版本的推荐评估使用相同输入。
字幕可用不代表内容适合。新增内容审核用于减少宣传介绍和无实质内容；保留少量
同主题但水平或形式不合适的内容，用于检验推荐的筛选能力。
自动审核不写入 Eval 的 `relevance`，也不将 `label_status` 标记为人工已复核。
人工标注后固定同一批视频，再比较推荐版本；更换候选库后的分数不能直接用于证明版本改进。

## How to test or use it

在项目根目录运行：

```powershell
uv run python scripts/crawl_eval_videos.py --profile data/eval-corpus/profile.json --output data/eval-corpus-incoming
```

`--profile` 支持当前独立画像 JSON，也支持包含 `profile` 字段的单条完整评估用例。
只接受一个画像，不支持多条 JSONL 用例。无需先给候选填写人工标签。
`data/eval-corpus` 是固定评估库；重新采集时使用尚不存在的临时目录
`data/eval-corpus-incoming`，确认结果后再整理到固定库，不再创建编号版本目录。

使用本机 `.env` 的现有配置：

- 文本模型：`TEXT_API_KEY` 或 `DASHSCOPE_API_KEY`，以及当前文本模型配置。
- 搜索：`SEARCH_API_KEY` 或 `DASHSCOPE_API_KEY`。
- 字幕：有效的 `BILI_SESSDATA`；其余 B 站登录字段沿用项目配置。

脚本会调用真实文本模型生成搜索词、执行画像初筛及字幕审核，并调用真实搜索服务，
因此会消耗对应额度，耗时也会比仅检查字幕更长。
它不生成 RAG 摘要或 Embedding，不运行推荐评估，也不写入真实推荐数据库。
现有凭据由 `Settings.from_env()` 读取，脚本不修改凭据。

### 输出

| 文件 | 内容 |
| --- | --- |
| `videos.json` | 实际采集成功、有字幕的视频，包括元数据和第 1P 字幕 |
| `manifest.json` | 数量、筛选规则、每条审核分数/理由/字幕证据、最终是否选中、模型调用用量和视频文件哈希 |
| `profile.json` | 本次使用的画像快照 |
| `bvids.txt` | 实际采集成功的视频 BV 号 |
| `searches.json` | 搜索词、候选 BV 号、筛选数量及淘汰原因，供后续扩展查询 |

检查命令最终输出的 `complete`、`video_count`、`positive_candidate_count`、
`hard_negative_candidate_count` 和 `stop_reason`。
`complete=true` 且 `video_count=30` 才表示已达到这次目标。
接口受限或候选不足时，文件里的实际数量可能小于 30，不能将其视为完成。

多P视频只采集第 1P；后续人工相关性评分应依据该部分内容。
先查看 `manifest.json` 的 `checks`：`accepted=true` 表示选入最终库，
`pool_role` 是模型建议分类，`reason/evidence` 是审核依据，`review_input` 说明字幕覆盖。
对最终全部候选独立人工评分，不直接把审核分数作为金标准。
视频库准备好后，在同目录创建一条包含该画像与全部候选人工评分的 `cases.jsonl`，
再按 [推荐四项 AI Eval](recommendation-evaluation.md) 运行评估。
采集、初筛及内容审核的调用用量在采集清单单独保存，不计入后续推荐运行的成本与延迟。

### 离线验证

```powershell
uv run pytest -q tests/test_crawl_eval_videos.py tests/test_eval_corpus.py
uv run ruff check src tests scripts/crawl_eval_videos.py
```

测试覆盖完整画像初筛、内容淘汰、介绍标题不能直接判坏、负样本数量及部分库比例上限、候选替换、证据归属、
长字幕覆盖与输入上限，以及无字幕替换、去重、HTTP 412、登录失败、预算、快照保护。
离线测试使用替身验证流程行为，不能证明真实模型的内容判断准确。
