## 1. 目标与可观察结果

改进“用户画像 → 查询向量 → 字幕证据”的输入，使检索更贴近学习主题、目标和内容偏好。
第一阶段建立“多个检索需求 → 多条查询文本 → 多个向量 → 检索与合并”的可执行流程，
第二阶段验证需求覆盖、融合参数与真实推荐效果。

完成第一阶段后，推荐流程将使用确定性规则生成的一组专用检索文本，而不是完整画像 JSON。
同一主题下的多个适用内容偏好也可以产生多个检索需求，每条查询单独生成向量。
推荐时间、数量和反馈证据 ID 的变化不应改变查询集合。
在不存在偏好冲突时，仅改变偏好来源标签也不应改变查询集合；来源参与冲突处理的情况单独验证。
完整画像仍提供给现有初筛和排序模型，时长限制、已看过和禁止推荐仍由现有流程处理。

第一阶段就包含基础 RRF 合并，最终每个视频仍返回最多 5 个字幕片段，
附带原有片段 ID、原文和时间范围。一个画像恰好只有一个独立检索需求时，保留单查询路径。
收益必须由真实字幕、真实 Embedding 与已复核标签的对照实验支持。

已确认的限制：

- 推荐初筛最多保留 20 个视频，摘要检索默认也取 20 个。因此摘要排序通常不会再减少候选；
  查询优化的主要可观察变化是字幕片段选择和后续评分，不能只看视频召回数量。
- 当前检索没有最低相似度门槛。返回前 5 个只表示相对靠前，不能据此认定它们足够相关。
- 默认 `evals/recommendation-cases.jsonl` 是 6 个合成视频、4 个画像的流程样例，标签待人工复核。
  离线模型使用确定性测试替身，其得分不能证明真实检索质量。
- 当前真实推荐评估从冷缓存开始，会重新生成摘要与索引。
  隔离查询改动时应复用同一份已建索引，避免摘要生成差异干扰比较。
- 当前项目未实现 RRF；RRF 也不自动保证每个主题都有证据。
- 查询数量应由独立检索需求决定。单个主题下有多个适用偏好时，也可能需要多个向量。
  Embedding 适配器每批 10 条是请求批次大小，不能当作一个画像的查询总数上限。

## 4. 范围与实施假设

第一阶段实现需求级查询构造、批量向量化、基础 RRF 合并和必要诊断。
第二阶段使用真实数据验证需求覆盖与推荐质量，必要时仅在 dev 集调整融合参数。

本次复用模型接口、SQLite 索引和现有排序模型。不更换模型、不升级依赖、不新增向量数据库，
不改字幕下载、语义分块、摘要提示词、用户记忆合并规则、每日去重或 API 端点。
不在第一阶段加入查询改写 LLM、BM25、独立重排模型、主题配额或相似度阈值。

仅改变查询文本和合并策略，无需重建字幕索引。若实施中发现必须改变索引表示，
先记录原因并重新明确范围，不把索引重建混入本实验。

真实评估使用独立数据目录，不改真实用户画像、反馈、推荐清单、凭据或 `.env`。
数据、模型版本、费用口径和本次验收目标在查看 test 结果前固定。

## 5. 第一阶段：需求级多查询与基础融合 B

### 5.1 查询构造规则

新增 `src/video_agent/retrieval_query.py`，提供共享函数：

```python
def build_retrieval_queries(profile: Profile) -> list[str]:
    ...
```

函数只读取画像，不修改画像、不调用模型。输出的是查询列表；每条查询都包含足够的
主题、目标与已有水平上下文，可以再围绕一个适用的正向内容偏好构造独立需求。

例如，画像明确表示学习 RAG 工程实践，并同时偏好理论讲解和代码实操，可以产生：

```text
Q1：学习主题：RAG；学习目标：实现一个 RAG 项目；已有水平：有 Python 基础。
Q2：学习主题：RAG；学习目标：实现一个 RAG 项目；已有水平：有 Python 基础；内容需求：理论讲解。
Q3：学习主题：RAG；学习目标：实现一个 RAG 项目；已有水平：有 Python 基础；内容需求：代码实操。
```

这里 Q1 是基础学习需求，Q2、Q3 是相同上下文下的不同偏好需求，分别生成三个向量。
不能把 Q2、Q3 仅写成“理论讲解”“代码实操”，否则容易召回其他主题的视频。
偏好不需要排列组合：不枚举所有偏好子集，也不把多个内容需求压回唯一查询。
这些查询支持找证据，最终是否同时满足多个偏好仍由完整画像下的排序模型判断。

规则如下：

1. 保留 `topics` 的用户顺序，去除首尾空白和完全重复的主题。
2. `goal` 非空时保留用户原文；不生成子目标，不从“避免入门”推断“要求高级”。
   原始目标可能含否定或多个主题，本阶段不宣称消除了其中全部歧义。
3. `level` 非空且不为默认“未指定”时纳入查询。
4. 对每个不同主题先生成一条“当前主题 + 整体目标 + 已有水平”的基础查询。
   整体目标保留原文，不猜测其中哪部分只属于某个主题，并记录重复目标可能产生的干扰。
5. 正向内容偏好只纳入 `direction=prefer` 且 `dimension` 为 `topic`、`depth` 或 `style` 的条目。
   每个适用的不同偏好分别生成“基础查询上下文 + 当前偏好内容”的查询。
   `global` 应用于各当前主题；`topic` 必须匹配当前主题。
   匹配采用去除首尾空白后的严格文本匹配，不新增模糊匹配或近义词映射。
6. `video` 范围的偏好不生成面向其他候选的查询，继续作为对应视频的评分上下文。
7. `avoid`、`duration`、`pace` 不生成正向检索偏好查询，仍完整提供给初筛与排序模型。
   字幕向量相似度不承担排除规则或声音节奏判断。
8. 显式和推断的正向偏好都可参与；相同 `(dimension, value, scope, scope_value)` 去重。
   同键存在显式 `avoid` 时，不把冲突的推断 `prefer` 加入查询。
   查询构造不改写原始偏好，完整画像中的其他冲突仍由现有排序规则处理。
9. 对现有规范值使用固定中文表达，例如 `practical` → “代码实操”、`theoretical` → “理论讲解”、
   `beginner` → “入门”、`intermediate` → “中级”、`advanced` → “高级”。其他值保留原文。
10. 对当前主题，若全局和主题偏好表达相同的 `dimension + value`，只生成一条偏好查询。
    文本完全相同的查询也只保留一次，避免重复查询在 RRF 中重复加分。
    按画像主题顺序生成基础查询及其偏好查询，保持可复现的输出顺序。
11. 不输出 `daily_time`、`daily_count`、`max_duration_minutes`、偏好 `source` 或 `evidence_ids`。
    来源只用于第 8 条的冲突处理。仅有主题时仍至少有一条基础查询。

去重前的查询数量为 `主题数 + Σ(各主题适用的正向内容偏好数)`，按需求逐条展开，不枚举偏好组合。
总数量可能超过 10，交由现有 Embedding 适配器分批处理；不静默截断偏好或主题。
真实评估前记录查询数并固定调用预算，预算不足时明确标记未完成，不能把截断结果当完整验证。

### 5.2 接入与诊断

- `Recommender.run()` 用共享函数替换当前 JSON 查询，向 `Rag.retrieve()` 传入查询列表。
- `evaluation._ranking_variant()` 使用同一函数；无记忆组仍先移除偏好，再构造查询。
  报告新增 `retrieval_queries` 保存实际传入检索的列表。原 `retrieval_query` 仅在单条查询时
  保存该字符串，多条时为 `null`；同步更新消费者和报告版本，不拼接列表伪装成单查询。
- `evaluation_reports.py` 的人工复核读取结构化 `profile`；对查询 JSON 的解析回退只用于旧报告。
  同步调整当前仅接受版本 2 的复核入口，保证新报告仍可导出和回填人工标签，并保留旧报告兼容检查。
- 明文检索用例 `_retrieval()` 继续使用其原有 `case["query"]`，不误套画像构造规则。
- 推荐评估继续通过真实 `Recommender.run()` 执行。为记录实际调用，可在 `Rag` 增加
  仅供内部评估读取的 `last_retrieval_trace`，每次检索开始重置，保存各查询文本与索引、
  算法版本、参数、每查询排名和返回视频与片段 ID。无候选或检索失败时不能残留上次结果。
- 诊断不写入对外推荐 payload，不保存 API 密钥；评估报告明确区分“未执行”“成功”和“失败”。
  使用该附加记录时维护报告版本，不改变现有四组推荐指标的定义。

### 5.3 向量化与合并规则

- `Rag.retrieve()` 扩展为接受字符串或字符串列表，保留所有现有字符串调用行为。
  去除重复查询；空查询列表明确报错。去重后只有一条时走现有单查询排序，避免不必要的 RRF。
- 调用 `embedding.embed(queries)`，一条文本对应一个向量，保持输入与返回向量顺序一致。
  不先拼接查询、不平均多个查询向量；单主题且多个偏好时同样走多向量路径。

初始实验参数固定为 `k=60`、视频候选窗口每查询 20、字幕候选窗口每查询每视频 10，
最终视频上限仍为 20，每视频片段上限仍为 5。参数在 dev 集选定后冻结；
10 个字幕候选是用于融合的窗口，不能误计为最终给模型的证据预算。

1. 对每条查询分别按摘要余弦相似度排列视频，取最多 20 个，按 BVID 合并其排名。
2. 对合并后的视频，分别按各查询的字幕余弦相似度排列片段，每份结果取最多 10 个。
3. 按片段 ID 计算 `rrf_score = sum(1 / (60 + rank))`，`rank` 从 1 开始。
   未出现在某份窗口内的片段，对该份结果贡献 0；同一 ID 在一份列表只计一次。
4. 按融合分数降序排列；分数相同按 BVID 或片段 ID 确定顺序，保证可复现。
5. 每视频取最多 5 个唯一片段，保留原文、ID、来源和时间戳。
6. RRF 分数与余弦相似度分别记录。返回结果的 `similarity` 保持余弦语义，
   多查询时定义为该片段对各查询的最大余弦相似度；融合分数和每查询排名放入内部诊断。
   不将 RRF 分数写进原有 `similarity` 字段，也不将其解释为相关概率或相似度阈值。

RRF 会偏向在多份结果中都靠前的内容。主题覆盖必须通过人工相关证据检查，
不能仅以“每个查询都返回了片段”认定覆盖成功。单主题下不同偏好的证据也必须分别检查，
例如找到实操片段不表示同时找到了理论讲解。覆盖情况在第二阶段按真实标签验收。

### 5.4 第一阶段验收

- 一个主题、两个不同适用内容偏好能生成基础查询和两条偏好查询，并获得三个对应向量。
- 不将理论、实操等多个内容偏好合并成唯一向量；每条偏好查询带有当前主题和目标上下文。
- 调度字段和证据 ID 的改变不会改变查询集合；无冲突偏好仅改变来源标签时，查询保持一致。
- 作用范围、显式与推断冲突、查询去重及超过 10 条时的分批行为符合约定。
- 推荐和画像排序评估使用同一构造逻辑，完整实际查询列表可从报告复核。
- 引用所属视频、时间范围、片段数量上限、无字幕补位及硬性时长筛选保持正确。
- 单字符串及单元素查询列表结果一致；空候选不调用 Embedding，原有索引空间检查仍生效。
- 每查询排名、RRF 公式、缺席项、去重、同分顺序和最终数量限制通过确定性测试。
- 不新增查询构造 LLM 调用。多查询会增加 Embedding 文本用量，按实际记录比较。
- 第一阶段通过表示多查询流程正确，真实质量保持待验收，不提前宣布召回提升。

## 6. 第二阶段：需求覆盖与真实效果验证

### 6.1 验证前提

B 已通过第一阶段功能验收，冻结语料中有相关字幕，并准备好主题、目标和偏好需求的
预先标注及独立人审。真实数据或人审不足时，保留质量待验收状态，说明缺少的证据。
多查询不再以“单查询效果不足”作为启动条件，它从第一阶段开始就是实现要求。

### 6.2 对照与参数候选

- 按第 7 节比较原始 JSON 方案 A 与需求级多查询方案 B。
  该比较衡量查询拆分与基础融合的整体效果，不单独归因于精简字段或 RRF。
- 分别检查单主题多偏好和多主题画像的需求覆盖，记录基础查询是否挤占了偏好证据名额。
- 若 dev 集失败案例表明融合参数有问题，调整 `k` 或候选窗口，形成候选 C。
  C 使用与 B 完全相同的查询集合，不重新引入“每主题只能一条查询”的限制。
- 在 dev 集选定后冻结参数再验证 test；不根据 test 失败逐例改参数。
  无需调整时不强行生成 C，只交付 A/B 验证结论。
- 若 RRF 持续压制只匹配一个需求的重要片段，记录失败；需求配额或其他融合方法
  另作后续决策，本计划不静默扩展算法范围。

### 6.3 质量验收

- 同一份已复核 test 数据上，B 的平均 Precision@5 与 NDCG@5 均不低于 A，至少一项提高；
  片段人工相关率不降低，单主题多偏好与多主题子集的需求覆盖均单独报告。
- 多需求 test 子集的需求覆盖率应高于 A；若 A 已完全覆盖，则要求不降低并检查其他收益。
  这些是本次计划的验收目标，尚非实测结论，小样本不能支持总体效果声明。
- C 只有在需求覆盖优于 B、整体推荐质量与片段相关率不降低时替换 B；不达标则保留 B。
  B 若也不满足对 A 的门槛，不将其宣布为质量优化成功，保留当前 A 并记录失败。
- 报告逐例结果、有效样本数、空结果、证据支持、额外查询数、请求数、token、费用与延迟。
  质量持平时只能报告多查询能力已实现，不能宣布效果提升。

| --- | --- | --- |
| A：当前基线 | 原始完整画像 JSON | 当前单查询余弦排序 |
| B：第一阶段 | 按主题及适用内容偏好生成多条查询 | 固定初始参数的 RRF；仅一条需求时用原单查询路径 |
| C：第二阶段参数候选 | 与 B 相同的查询集合 | 仅调整 dev 集选定的融合参数 |

新增单用途脚本 `scripts/compare_profile_retrieval.py`，只用于本次比较。
不增加生产环境策略开关或改动 `video-agent eval` 的公开命令参数。
实验脚本在独立进程内切换实际使用的查询构造函数，复用应用检索和推荐逻辑，
不能另写一份“实验专用 RRF”代替业务实现。B 完成后比较 A/B，
仅在第二阶段确实形成了参数候选时比较 B/C；无需调整时不生成 C。

### 7.2 数据和标注

- 使用冻结的真实 `videos.json`、`manifest.json` 及推荐 `cases.jsonl`，全部位于独立实验目录。
  推荐评估沿用最多 30 个视频、`daily_count=5` 和每个候选完整 0–3 分标签的现有约束。
- 准备至少 6 个真实画像场景，包含单主题、多主题、不同水平、正向偏好、负向偏好，
  以及主题范围和视频范围的偏好。至少 2 个场景为“单主题 + 多个内容偏好”，
  至少 2 个场景为多主题；语料中分别存在这些需求的真实相关字幕。
- 在运行 A/B/C 前标注“画像需求 × 视频”的适合度及相关原始字幕时间范围；
  允许多个正确片段和视频，不只挑某个策略已经返回的结果进行标注。
- 标注实际需求覆盖，不能把所有已有基础词当作要学习的主题。
  没有任何相关字幕的场景单独统计无匹配行为，不从数据中删掉困难样本。
- 开发场景和测试场景按需求划分；同一需求的改写不能跨 dev/test。
  代理草拟标签保留 `needs_human_review`，人复核后才能标 `human_reviewed`。

### 7.3 两种比较口径

**查询隔离实验：** 在临时 SQLite 中一次性建立固定摘要及字幕索引，A/B/C 共享相同索引内容，
使用同一画像下相同候选集和时长过滤，直接比较返回的片段。报告索引内容指纹、
Embedding 空间、实际查询、参数、候选和返回 ID，以及仅检索阶段的用量与耗时。

**完整推荐实验：** 复用现有冻结语料推荐评估，比较最终 Precision@5、NDCG@5、
Diversity@5、费用和延迟。各策略使用独立数据库，并记录初筛后的实际候选。
冷缓存索引生成和 LLM 初筛可能带来差异，此结果作为端到端效果，不能全部归因于查询改动。
若差值接近运行波动，在预先约定的调用预算内重复同一批用例，报告全部运行。

补充人工指标写在单独比较报告中，不改变现有四组指标的定义：

- 片段人工相关率 = 与预先标注学习需求相关的唯一返回片段数 / 全部唯一返回片段数。
  无片段时该率为 `null`，同时报告空结果和未覆盖需求，不能靠少返回提高相关率。
- 需求覆盖率 = 有至少一个相关返回片段支持的可回答需求数 / 全部可回答需求数。
  按单主题单需求 / 单主题多偏好 / 多主题及 dev / test 分组，同时列明语料不可回答的需求数。
  多个偏好分别有证据才算覆盖，不能用基础主题片段替代全部偏好的证据。
- 推荐理由证据支持：对实际引用片段人工复核；同一人的复核应尽量隐藏策略名称。

少量固定样本、未经人审标签或仅有离线替身时，只能交付实现与流程验证，质量验收保持待完成。

## 10. 关键测试（Validation）

第一阶段重点检查：

- 相同学习需求、不同时间 / 数量 / 证据 ID，查询集合一致；无冲突偏好改变来源标签时也一致。
- 默认空目标或未指定水平不引入虚构内容；仅有主题仍可检索。
- 单主题两个独立正向内容偏好产生三条查询及三个对应向量；增加适用偏好会新增对应查询。
- 每条偏好查询保留主题、目标和水平；多个偏好不排列组合，也不拼接后只生成一个向量。
- 正向全局偏好、匹配 / 未匹配主题偏好、视频偏好和负向偏好按约定处理。
- 显式 avoid 与同键推断 prefer 冲突时，查询不加入冲突正向偏好。
- 重复偏好及同主题下重复的全局 / 主题偏好不重复向量化或重复加分。
- 推荐与有记忆评估查询一致；无记忆评估查询中不混入偏好。
- 新多查询报告与旧报告的人工复核均能读取正确画像、导出模板和回填标签。
- 诊断保存完整查询列表和每查询结果，空候选或失败后不使用上次成功结果。

第一阶段同时使用可控假向量检查数学行为，不用假向量声称语义效果：

- 构造两份排名，手算 RRF，核对顺序、缺席贡献、去重和同分结果。
- 单查询兼容、多个查询批量顺序、重复查询、空查询列表、无索引视频和索引空间不一致。
- 查询数超过 10 时，适配器分批且每条仍对应一个向量，没有主题或偏好被静默截断。
- 单查询窗口少于 10、最终候选少于 5，以及跨视频相同文本具有不同片段 ID 的情况。
- RRF 分数和余弦相似度不混淆，输出的 ID、文本和时间戳保持来源一致。

第二阶段检查同一主题的理论 / 实操等不同偏好分别有证据的真实场景，
以及多主题各有相关证据、通用片段挤掉特定需求片段的失败场景。

## 12. 决策记录（Decision Log）

- 2026-10-09（修订）：第一阶段直接实现需求级多查询，取代最初的精简单查询方案。
  理由：用户指出同一画像、同一主题下的多个偏好也可能需要多个查询向量。
- 2026-10-09：完整画像继续用于评分，查询仅表达适用内容需求。理由：向量相似度不能执行全部偏好规则。
- 2026-10-09（修订）：查询按当前主题和适用内容偏好分别构造，不自动生成子目标。
  理由：多个偏好不应只能共同进入一个向量；每条偏好查询也需要保留学习上下文。
- 2026-10-09（修订）：基础 RRF 前移到第一阶段，第二阶段验证需求覆盖与融合参数。
  理由：多查询结果必须合并到每视频最多 5 个片段，才能形成完整可执行流程。
- 2026-10-09（修订）：查询数量按去重后独立需求计算；每批 10 条仅是现有适配器的批次大小。
  理由：不能把模型调用批次上限误写为一个画像的需求上限。
- 2026-10-09：保留查询隔离与完整推荐两种评估口径。
  理由：当前冷缓存摘要生成和初筛波动会混入查询效果比较。

RRF 公式参考：[Elastic 官方说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)、
[Microsoft 多查询排名融合说明](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)。
本项目使用本地排名计算，不依赖这两个产品的服务或 SDK。
